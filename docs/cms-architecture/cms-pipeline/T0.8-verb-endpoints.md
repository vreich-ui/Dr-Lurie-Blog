# T0.8 — Verb Endpoints (Dual-Auth Pair)

**Phase 0 · depends_on: T0.4, T0.5, T0.6, T0.7 · mode: auto · model: Opus 4.8 · effort: high**
**Blocks:** T0.9, T0.11.

## Why Opus / high effort
Security-adjacent (dual auth, credential isolation) and integration-heavy, but well-specified — Opus 4.8 is the right level; save Fable budget for T0.5/T0.6 where the correctness risk is higher.

## Read first
`docs/cms-architecture/01-audit.md` §1.2 (the existing dual-auth model and conflict codes) and `03-mapping-and-agent-contract.md` §2.0 (the verb surface, Principal attribution).

## Context
Two parallel entry points expose the object verbs: one authenticated by the shared publish key (for agents/scripts), one mirrored behind Netlify Identity (for the browser admin UI). Critically, the browser path must never see the publish key.

## Scope — files to create
- `netlify/functions/object-store.ts` — publish-key auth. Actions: `get / list / create / checkout / refresh_lock / checkin / patch / validate`. (submit/publish arrive in P1 — not here.)
- `netlify/functions/admin-object.ts` — Netlify-Identity mirror. **The browser never sees the publish key** (A§1.2).

## Deliver
- The C§2.0 verb surface **minus review/publish**.
- `expected_record_version` mismatch → **409**; lock conflicts → **423**. Both coexist exactly as audited (A§1.2) — don't collapse them into one code.
- Every write appends a history entry with `Principal` attribution (self-declared `agent_name` on the key path — today's trust model, C§2.0; do not build per-agent credentials here, that's OQ-3).
- **Server-side opaque-id minting before the patch grammar (added after T0.6 landed — PR #347).** T0.6's `object-patch-ops.ts` accepts *canonical* ops: every opaque id it carries (taxonomy `term_id`, new section `s_` ids, nav item/group ids, template slot ids) must already be present and valid. The documented agent request for `add_term` sends `term:{slug,label}` with the `term_id` "minted server-side" (C§2.5-C); that minting is **this endpoint's job** — mint the `t_<…>` id (per-type validator, T0.3) from the agent's `{slug,label}` and construct the canonical `add_term` op before calling the apply engine. Same pattern for any op that introduces a new opaque-id-bearing element from partial agent input. Do this at the endpoint, not inside the pure apply engine, so inverse restores stay exact.

## Non-goals
- No submit/publish/review actions (Phase 1).
- Do not change the existing article endpoints.

## Acceptance criteria
- `tests/netlify/object-store-*.test.ts` integration suite drives **both** auth paths against the local blob fallback.
- Conflict-code parity assertions (409 vs 423 in the right situations).
- A test confirming the admin/browser path never receives or requires the publish key.
- Committed to the working branch. No PR unless asked.
