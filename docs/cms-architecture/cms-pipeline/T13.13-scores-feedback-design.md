## Context

Today `scores[]` is exclusively agent-authored; nothing may change about that until this design is ruled on.

## Scope — the design must answer (deliverable = a new §15 appendix in doc 12)

- **Provenance:** how a metric-derived entry is distinguishable from an agent judgment forever — proposed: `scored_by` carries a namespaced identity (`metric:<framework>`), plus REQUIRED window/sample fields (`window_start/end`, `n_sessions`, `source: tracking_event.v1`) so a score is never quoted without its evidence base.
- **Transport:** who writes the entry and through what — options to weigh: (a) the owner DB computes and an agent submits via the normal `object_patch` path (recommended start: keeps every write inside the governed grammar), (b) a dedicated MCP tool (`article_record_metric_score`) with its own validation, (c) fully automatic writer (argue why NOT, given the trust model and OQ-3).
- **Guard rules (hard):** metrics may only APPEND scores — never mutate/delete agent scores, never change content, never trigger publish/release; leak rule untouched (scores stay non-rendered); rate/threshold rules so noisy small-sample scores can't flood the envelope (`n_sessions` minimum).
- **Variant judging:** how scores on a variant (`lineage.parent_content_id`) compare against the parent — the create_variant/A-B loop this exists to serve — WITHOUT implying traffic splitting (OQ-W7-2 stays deferred; comparisons run on sequential or organic exposure only, stated honestly).
- **Multi-project:** framework definitions live in core; per-site thresholds are data.
- **New OQs** for Wolf if any emerge (numbered OQ-W13-7+ in doc 12 §13).
