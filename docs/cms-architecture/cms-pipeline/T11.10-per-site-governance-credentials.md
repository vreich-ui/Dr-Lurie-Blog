## Context
At fleet scale, one shared key + self-declared `agent_name` stops being tolerable: creation-policy allowlists, theme-maker restrictions, and audit attribution all assume identity. Scope is the MINIMAL slice per Wolf's OQ-W11-5 ruling — verifiable per-agent tokens, not a full IAM.

## Scope — files to create/modify
- Per-agent credentials (if ratified): an `agent-keys` doc in the governance store (hashed tokens, `agent_name`, status, created_by, per-site) + MCP auth accepting `Authorization: Bearer <agent token>` resolved to a VERIFIED agent principal; the shared `MCP_HTTP_AUTH_TOKEN` remains as a deprecated fallback flagged in history attribution. Creation-policy allowlists + history `agent_name` switch to the verified identity when present.
- Per-site posture files: `sites/<client>/config/approval-policy.ts` + `creation-policy.ts` (drlurie keeps current values verbatim); core resolvers take them via the site binding (seam laid in T11.2 — wire it).
- ✚ `docs/cms-architecture/secrets-runbook.md`: per-site secret inventory, generation, storage, and rotation procedure — including the standing `PUBLISH_SECRET` rotation debt (execution itself is a human act; runbook makes it one page).
- Adversarial tests: forged agent_name without token ≠ verified; revoked key fails closed; per-site key never crosses bindings; approval decisions still human-only (M-6 posture unchanged).

## Deliver
Identity-grade agent attribution (per ruling), per-site posture files, and a secrets runbook that ends the shared-key era on a schedule Wolf controls.

## Non-goals
- No agent-approves-agent review (M-6 stays human-only). No SSO/OAuth. No forced cutover of existing integrations — fallback deprecation is flagged, not enforced here.

## Acceptance criteria
