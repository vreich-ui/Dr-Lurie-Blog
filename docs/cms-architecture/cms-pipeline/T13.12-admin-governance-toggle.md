## Context

OQ-W13-2 (2026-07-19): tracking_config publish autonomy is config-driven — "auto if configured in config" — and the owner must be able to SEE and CHANGE that posture from the admin UI, not only by editing a committed file. The flip mechanism depends on Wolf's T9.15 ruling: if the runtime override layer exists, the toggle flips it live (Owner-only); if Wolf ruled commit-only, this surface is a read-only posture view + a guided config-file change (prepared diff / instructions), never a silent runtime mutation.

## Scope — files to create/modify

- New admin surface (placement per the W9 shell conventions, e.g. a "Tracking" card under the existing settings/governance area): shows tracking_config's CURRENT effective posture (publish: autonomous/require-approval; creation: humans-only) read from the live policy readers — never hardcoded.
- Flip flow, branched on the T9.15 outcome:
  - Override layer BUILT → Owner-only toggle writing the runtime override (same auth boundary T9.15 defines; audit-logged).
  - Commit-only ruling → read-only badge + "how to change" affordance (the exact one-line `src/config/approval-policy.ts` edit, copy-ready).
- Show the same view for `product` (the other pinned type) so the surface is honest about ALL posture pins, but tracking is the entry point — do NOT build a general per-type policy matrix (T9.15's scope).
- Tests: posture rendered from config truth (flip the config in a fixture, UI follows); Owner-gating on any write path; no write path at all in commit-only mode.

## Deliver

An owner opens the admin and can answer "who may publish tracking_config right now?" in one glance, and change it through whichever mechanism T9.15 sanctioned.

## Non-goals

No general governance UI for all types (T9.15). No new auth machinery. No tracking_config BODY editing (that's the normal object workspace). No policy changes themselves — this task surfaces and flips, it doesn't re-decide defaults.
