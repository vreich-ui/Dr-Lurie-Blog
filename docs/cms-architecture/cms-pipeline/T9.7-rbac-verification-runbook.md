# T9.7 — RBAC credentialed verification runbook (wave-exit W9.b)

**Status: prepared, awaiting a human driver.** This is the human_gate for W9.b:
the two-tier role model (T9.4) and the admins/invite surface (T9.5/T9.6) are
proven headlessly by 1400+ unit tests, but house convention holds that security
work isn't *shipped* until proven on the deployed site with real credentials and
a real second identity. No product code is changed by this task — anything a run
uncovers becomes its own follow-up task.

The mechanical, repeatable half (the server-side 403 proofs and the auth-state
tier checks) is automated by `scripts/rbac-verify.sh` in this directory. The
human half (a real invite email, a second login, a lock takeover) is the
checklist below. Record the outcome in `state-of-play.md` using the template at
the end — that entry *is* the wave exit.

## What "server-side proof" means here

UI-hiding is not access control. Every denial below must be demonstrated by a
direct authenticated function call returning **403**, not merely by a menu item
being absent. The automated script does exactly this: it sends the *Admin's*
bearer token to owner-only endpoints and asserts a 403 before any mutation runs.
(The probes it sends are denied at the role gate, which is checked before the
request body is even dispatched, so the script is side-effect-free and safe to
re-run.)

## Prerequisites

- A deploy to verify against: production or a Netlify deploy preview. Note the
  base URL (e.g. `https://<deploy>.netlify.app`).
- **Owner token**: sign in as an `ADMIN_EMAILS` bootstrap owner; copy the GoTrue
  access token (DevTools → Application → Local Storage → `gotrue.user` →
  `access_token`, or from the network tab's `Authorization` header).
- **Admin token**: the second identity from step 1 below, after it has accepted
  the invite and logged in once (so its record is `active` and role `admin`).

## Automated pass (server-side denials + tier resolution)

```bash
SITE_URL="https://<deploy>.netlify.app" \
OWNER_TOKEN="<owner access token>" \
ADMIN_TOKEN="<admin access token>" \
bash docs/cms-architecture/cms-pipeline/scripts/rbac-verify.sh
```

It asserts, and prints PASS/FAIL for each:

- `admin-auth-state` resolves the Owner token to `tier: "owner"` and the Admin
  token to `tier: "admin"`.
- With the **Admin** token, every owner-only endpoint returns 403:
  `admin-users` verbs `list` / `invite` / `set_role` / `disable`;
  `admin-governance` verb `set`; `admin-blob-manager`; and `admin-object`
  `checkin` with `force: true` (the owner-only lock takeover option).
- With the Admin token, the Admin-readable endpoints still return 200:
  `admin-governance` verb `get`; `admin-object` verb `inventory`; `admin-audit`.
- With the **Owner** token, the owner-only reads (`admin-users` `list`) return
  200 — proving the gate is a role check, not a blanket block.

A non-zero exit means at least one assertion failed; read the per-line output.

## Human checklist (the credentialed gate)

Drive these in order on the deploy. Record each outcome.

1. **Invite → accept → activate.** As Owner, `/admin/settings/admins` → invite a
   *fresh real email you control* as Admin. Confirm: the invite email arrives,
   the accept link works, and first login flips the member from `invited` to
   `active` (visible in the admins roster and in `admin-auth-state.roles`).
2. **Admin can edit content.** As the new Admin, open an object in the
   workspace, check it out, patch a field, publish (if the type is autonomous) —
   editing works end to end.
3. **Admin is walled from owner surfaces — server-side.** As the Admin:
   `/admin/settings/admins`, `/admin/settings/guardrails`, and
   `/admin/maintenance` are hidden in the nav **and** the underlying owner-only
   calls 403 (the automated pass proves this with the Admin's own token; spot-
   check one by hand with `curl` if you want to see it live).
4. **Bootstrap fallback (no lockout).** In a non-production store copy (or via
   the documented test hook), rename/suffix the users-store doc so the record
   layer is effectively empty; confirm an `ADMIN_EMAILS` member still resolves
   `owner` from `admin-auth-state`. (Never do this against the production store.)
5. **Lock takeover is attributed.** Admin checks out an object and holds it.
   Owner force-checks-in (`checkin { force: true }`). Confirm: the object's
   history shows the takeover attributed to the Owner as the actor, and the
   Admin's next patch against the stale lock fails with 409/423 rather than
   silently succeeding.
6. **Disable revokes everything.** Owner disables the test account. Confirm all
   access is revoked server-side: `admin-auth-state` for that token now resolves
   no admin role, and a content mutation with it 403s.
