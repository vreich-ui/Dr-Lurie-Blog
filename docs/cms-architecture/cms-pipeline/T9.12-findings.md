## Verdict

**The central mechanic works within the constraints we can prove from a branch:
pause on an ask-gated tool call, persist to the blob store, resume on a later
invocation with the stored call re-verified.** All four brief mechanics plus
the forged-resume rejection are proven by `tests/netlify/spike-agent.test.ts`
(4/4) against the real `handleObjectVerb` core and the real state-machine code
that the deployed functions run — the only mocked seam is the provider
adapter (scripted turns) and the HTTP hop between the two functions (direct
invocation). **Deploy-level timing was NOT exercised in this run**: this
branch has no Netlify deploy (functions deploy on merge; production deploys
are commit-locked), so cold-start/15-min-budget numbers below come from the
2026-07-19 artifact-drill evidence, and the ≥60 s-pause + deployed-function
acceptance items are carried into the T9.16 credentialed drive
(`scripts/spike-agent-driver.mjs` is ready to run against any deploy that
carries the spike). This is the same branch-proof/live-drill split the
07-19 artifact session used.

## What is proven (test-by-test)

1. **Read tool auto-executes; event log advances seq; `since_seq` slices
   correctly** — get_object runs via `handleObjectVerb` with no approval;
   usage accounting flows from the adapter into the run record.
2. **The pause survives invocations.** An ask-gated `propose_patch` puts the
   doc at `awaiting_approval` with `{call_id, tool, args, args_hash}` and the
   function RETURNS. A fresh invocation reads it all back. **Approve executes
   the STORED args under the run's original HUMAN principal** — the patch
   lands with `actor: {kind:'human', id, email}` in object history, the
   checkout→patch→checkin cycle leaves no lock behind, and the next hop
   finishes the model turn. **A replay of a consumed trigger token is inert.**
3. **Forged resume rejected** (the 2026-07-15 forged-entry lesson): wrong
   `call_id` → 409 `forged_resume`; stored args tampered without the hash →
   409 (re-hash mismatch); approve after deny → 409. Client-supplied args are
   never read — approve takes `(chat_id, call_id)` only.
4. **Deny feeds a refusal tool-result** back to the model (`is_error: true`)
   and the run continues to a graceful `idle` with no write.

## Design decisions validated → carry into T9.13

- **One chat doc per chat** (`chats/<id>.json`, `:` → `__` in the blob key for
  the `obj:<objectId>` convention): seq-ordered `events[]` + the run state in
  one JSON. Polling = `events.filter(seq > since_seq)`. No index doc needed.
- **Single-writer state machine instead of CAS** — Netlify Blobs has no
  compare-and-swap on update, so correctness comes from state ownership:
  `queued` (only the token-holding background hop may take it) → `running`
  (only that hop writes) → `awaiting_approval` (only approve/deny write) →
  `queued` → … → `idle`. Every transition has exactly one legal writer.
- **One-shot trigger tokens** authenticate the public background URL:
  send/approve/deny mint a token into the doc, the background hop consumes it
  on start. Replays/forged POSTs hit `not queued or bad trigger token`. The
  identity-authenticated function never touches the publish key (A§1.2
  posture preserved).
- **Provider-neutral transcript stored in the run; stateless re-send.** The
  adapter maps neutral → wire format per call. This is what makes pause/resume
  trivial AND what makes the dual-provider requirement (OQ-W9-3) cheap: the
  OpenAI adapter is a second mapping over the same transcript.
- **`call_queue` for multi-tool turns**: a turn like [read, write] executes
  the read, pauses on the write, and the queue drains after approve — so the
  provider only ever sees a complete set of tool results per turn (Anthropic
  requires every `tool_use` answered in the NEXT message; consecutive tool
  results must merge into ONE user message — implemented and exercised).

## Provider notes (Anthropic adapter, `@anthropic-ai/sdk@0.112.3`)

- Default model `claude-opus-4-8`; **no `temperature`/`top_p`/`top_k`** (400
  on Opus 4.7+) and **no `budget_tokens`** (removed). v1 runs with `thinking`
  omitted → no thinking blocks → the neutral transcript round-trips exactly.
  Adaptive thinking is a marked upgrade seam: enabling it requires persisting
  provider-native assistant blocks (thinking blocks must be echoed back
  unchanged on the same model), i.e. a raw-blocks side-channel in the run
  record — do NOT enable it casually in T9.13.
- `max_tokens: 16000` per turn (non-streaming; background function has no
  client waiting, so streaming buys nothing — polling reads the event log).
- Tool defs: JSON Schema `input_schema` with `additionalProperties: false`;
  parallel tool_use is on by default — handled via call_queue (above).
- `openai@6.48.0` is installed for T9.13's second adapter (chat-completions
  `tools:[{type:'function',…}]` mapping over the same neutral transcript).
- Keys: `ANTHROPIC_API_KEY` (present in Netlify env per the brief) /
  `OPENAI_API_KEY` (already used by run-publisher-agent).

## Timing & platform constraints (from adjacent live evidence, 07-19 drill)

- Cold starts on this site's functions: first calls can take tens of seconds
  (two 60 s first-call timeouts observed on external MCP legs; the site's own
  mcp function keeps a 5-min keepalive schedule for exactly this reason).
  Consequence for chat UX: the FIRST hop after idle may take 5–20 s before
  events appear — the UI polls, so nothing breaks, but T9.14 should render a
  "waking the agent" state. A keepalive for the chat background function is
  NOT recommended yet (cost; revisit after T9.16 numbers).
- 15-min background budget: a hop is one provider turn + tools, well under
  budget; the pause/resume structure means a run never needs the full window.
  Recommended caps to start T9.13: `maxProviderTurns 12`, `maxToolCalls 16`,
  `maxOutputTokens/run 60_000`, wall-clock guard 12 min via
  `context.getRemainingTimeInMillis` when available.
- Event-write cadence: one `setJSON` per event on a strong-consistency store
  was instant against the local store and is the simplest correct thing;
  revisit only if the doc grows past ~500 events (cap + trim in T9.13).

## Known gaps T9.13 must close (found by the spike)

1. **Stuck-`queued` recovery**: if the background trigger POST is lost, the
   doc stays `queued` with a live token forever. T9.13: `get_chat` surfaces
   `queued_since`; a `send`/`cancel` on a stale queued/running doc (updated_at
   older than the wall-clock cap) may take over and re-arm.
2. **Stuck-`running` recovery**: a crashed hop leaves `running`. Same
   staleness takeover applies.
3. **Edit-and-approve** is deliberately absent from the spike: production
   accepts human-EDITED args on approve, re-validated against the tool's
   schema and recorded as an edit by the approver — the no-client-args rule
   holds for plain approve only.
4. The spike's `propose_patch` bundles checkout→patch→checkin per call;
   production tools expose the real verb surface (checkout/patch/checkin as
   separate tools per the §4 registry) with per-op contract validation.
