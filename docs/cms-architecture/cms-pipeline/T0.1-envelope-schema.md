# T0.1 — Envelope Schema Module

**Phase 0 · depends_on: none · mode: auto · model: Sonnet 5 · effort: medium**
**Blocks:** almost everything in Phase 0 — this is the shared shape every object type wraps.

## Read first
Before writing code, read `docs/cms-architecture/cms-architecture-consolidated.md` §2 (the envelope) and, for full detail, `docs/cms-architecture/02-architecture-and-schema.md` §3.1. This brief is deliberately terse and assumes that context.

## Context
Every CMS object type — Page, Section, Navigation, Taxonomy, Site, Template — shares one wrapper record. This task defines that wrapper as a zod schema. Nothing type-specific goes here; the per-type bodies are T0.2.

## Scope — files to create
- `src/schema/object-record-v1.ts`

## Deliver
The `ObjectRecord` envelope exactly per D§3.1: fields `object_id`, `object_type`, `schema_version`, `site`, `status`, `body`, `publication`, `review?`, `lock?`, `history`, `version`, `content_revision`.
- `HistoryEntry` carries a structured `actor: Principal` (see D§3.9 for the Principal shape).
- The `workflow` extension field is typed but unused — articles are not migrated into this envelope (D§1), it's a forward hook only.
- **Import and re-export the lock record shape from the existing `schema-v1.ts`** rather than redefining it — this is what makes human/agent lock parity true by construction (A§1.2). Do not define a new lock shape.

## Non-goals
- No per-type body schemas (that's T0.2).
- Do not define validators or ID rules (T0.3).
- Do not touch `schema-v1.ts` — only import from it.

## Acceptance criteria
- Unit tests: zod round-trips a valid envelope; the envelope rejects an unknown `object_type`.
- A test proving `content_revision` and `version` are **independent** counters (one can change without the other) — this distinction is load-bearing later, so lock it down now.
- Committed to the working branch. No PR unless asked.
